# Eval report — einvoice-agent

What the evals in [EVAL_PLAN.md](../EVAL_PLAN.md) measured, how, what came out, and what the numbers do
not show. Everything here is on **synthetic data**: no real invoice has been run (see
[Known limits](#known-limits)).

The tables under [Results](#results) are generated by `make eval-report` from what `make eval-full`
leaves in `eval/out/`; do not edit them by hand. The rest of this page is written, and refers to the
state of 2026-11-14 (thresholds `2026-11-14.1`, model `claude-opus-5-5`).

The four regression gates of EVAL_PLAN §7 run in CI on every push: structured field accuracy below
100 % fails (`make eval-quick`, 51 documents); any injection that works fails (`make eval-probes`); a
changed-IBAN or duplicate recall below 95 % fails (`make eval-exceptions`); an auto-rate more than
5 points below the fitted one warns (`make eval-decision-pdf`). Matching below 95 % also fails.

## Method

**Sets.** All generated from seed 20261113, split 70 % dev / 30 % held-out by document. Thresholds,
calibration and every rule change were made on dev; the reported numbers are the held-out split.

| Set | Size | Made by | Ground truth |
|---|---|---|---|
| Structured | 200 invoices × UBL, CII, ZUGFeRD = 600 files | `eval/generators/structured.py` | the generator's invoice; parsers also checked against the official XRechnung test suite and ZUGFeRD samples ([D10](../ARCHITECTURE.md#5-design-decisions-adr-log)) |
| Text PDFs | 150 (114 dev / 36 held-out) | `eval/generators/pdf.py`, 10+ layouts, DE/EN; held-out layouts never seen on dev | the canonical invoice behind the PDF |
| Scans | 100 (76 / 24) | `eval/generators/scans.py`: the PDFs rasterised, skewed, blurred, stamped, JPEG-compressed | as for PDFs |
| Matching world | 50 suppliers, 425 invoices (124 held-out), orders, deliveries, bank transfers with partials, combined payments and typos | `eval/generators/world.py` | the world's links |
| Exceptions | 240 cases: 120 with one planted problem (6 kinds × 20), 120 clean | `eval/generators/exceptions.py` | the planted problem |
| Injection probes | 20 PDFs with instructions in a note or hidden text, each with a control without them | `eval/generators/probes.py` | the control's outcome |

**Systems.** The rule-based baseline (templates and regular expressions over the text layer, OCR for
scans; exact-key matching), the model alone (`llm`: system 2, "LLM extraction only"), and the
application's pipeline (`llm-rules`: structured-first, then the model, the completion rules,
confidence, checks, matching and the decision engine).

**Scoring.** A field is right when gold and prediction are equal after both are loaded into the invoice
model (so `1.5` and `1.50` are one amount). A field that is missing, or that the prediction adds, is
wrong. Line items and VAT groups are compared field by field. The scorer is tested against hand-computed
cases (`tests/eval/test_score.py`), and so is this report (`tests/eval/test_report.py`).

**Model calls.** Every answer of `claude-opus-5-5` is recorded and replayed from `eval/recordings/`:
re-running costs nothing and gives the same numbers. Extraction ran three times (EVAL_PLAN §5): run 1 on
2026-11-13 (250 calls), runs 2 and 3 on 2026-11-15 (250 calls each, in `run-2/` and `run-3/`, 17.11 USD);
numbers on PDFs and scans are mean ± sample standard deviation over the three. The 40 probe calls ran once. The text PDFs are byte-identical across machines, so CI replays them; the scans are not
(floating-point image operations), so their recordings replay only on the machine that made them.

**Decision threshold.** The confidence threshold is fitted on dev by loosening it from the strictest
value only while the documents each step adds are wrong at most 1 % of the time (`eval/sweep.py`).
EVAL_PLAN's literal rule ("highest auto-rate with error ≤ 1 %") was dropped: it picked 0.33, which let
in exactly one extra document, the one wrong scan, because 1 in 157 fits the budget.

**Error bounds.** Where nothing went wrong, the report gives the one-sided 95 % upper bound
(Clopper–Pearson) instead of "0 %": 0 wrong of 45 means "at most 6.4 %", not "never".

**Reproduce.** `make up && make ocr-data && make eval-full` (3½ minutes, no API key). New model answers:
`make eval-pdf-llm-record` and `make eval-probes-record` (paid, key in `.env`).

## Worst 10 cases

The ten cases, from every eval and both splits, that did or could have done the most damage, worst
first. A wrong booking ranks above a needless review.

1. **A field left out, booked without a person** (`pdf-0142`, held-out, runs 2 and 3). The PDF prints
   the buyer reference ("Client ref.: 90000000-03083-72"); run 1 read it, runs 2 and 3 left it out. A
   missing field has no confidence to be low, and the buyer reference is not among the fields the decision
   requires, so the invoice went through: the only held-out error of the pipeline in three runs. The
   booking itself would have been right (the buyer reference is not booked), but the invoice of record
   lacks a printed field. One run would not have shown it. **Open**: the blind spot of case 2 below,
   seen on the model's own output.
2. **The confidence gate lets through errors it cannot see** (baseline stress test, dev). Run on the
   baseline extractor's output, the threshold that holds back the model's one low-confidence misread lets
   29 of 32 wrong baseline scans through, for example `scan-0005` with its line items read wrong. Two
   blind spots: a value is "found in the text" even when it belongs to another field (quantity and price
   swapped also pass quantity × price), and something left out has no confidence to be low. **Open**:
   no second, independent signal yet.
3. **Misreads held back only by an unrelated rule** (`scan-0002` seller VAT ID, `scan-0098` buyer
   reference, dev, run 1). Both had high confidence and went to review only because the currency was
   assumed, not printed. Had the currency been on the page, both would have been booked wrong. With
   `scan-0059` (wrong issue date, held back because a field was missing), **only 1 of the 4 remaining
   misreads was caught by confidence itself**: `scan-0000`, a misread IBAN at confidence 0.33 (see the
   table under Results). The low error count leans on the currency rule. **Open.**
4. **An invoice marked paid with its twin's money** (matching, found while testing re-matching). With an
   invoice's own transfer still missing, the matcher took an unreferenced transfer of the same amount
   that paid a twin invoice not yet on file, and nothing would have corrected it. **Fixed**: a payment
   matched by amount alone keeps the invoice open until a transfer quoting it arrives.
5. **Credit notes would have been booked as invoices** (delivery design). A booking carries no sign.
   **Fixed**: only invoices (type 380) are delivered; credit notes stay in review ([D9](../ARCHITECTURE.md#5-design-decisions-adr-log)).
6. **The threshold rule picked the one wrong document** (decision sweep). See Method. **Fixed** by the
   marginal rule.
7. **A re-issued invoice went unnoticed** (exceptions, 2 of 2 cases). Same delivery, new number, later
   date: no duplicate rule fired. **Fixed**: `delivery_already_billed`, another document matched to the
   same delivery.
8. **Totals that are not printed** (model alone: 24 of 36 held-out PDFs, 15 of 24 scans). Every
   model-alone error is `vat_total` or `currency` on layouts that print neither. The model was right not
   to invent them; the gold counted them because it comes from the canonical invoice. The completion
   rules fill them in, marked as derived; an assumed currency always goes to review, which is all of
   the 25 % not booked automatically on the held-out split.
9. **Templates do not carry over to new layouts** (baseline, held-out). The baseline reads 99.84 % on the
   dev layouts and 44.99 % on the unseen ones (`pdf-0045`: 56 wrong fields). This is the case for the
   model, and the reason the held-out layouts exist.
10. **Clean invoices flagged** (exceptions, first run). A VAT amount rounded the other way by one cent
    failed the totals check (6 of 10 rounding near misses), and a supplier's next invoice for an equal
    part delivery looked like a near-duplicate (3 of 90). **Fixed**, with unit tests; both cost a person's
    time, not a wrong booking.

## Lessons learned

- **The eval found more defects than the unit tests did.** The three check fixes, the twin-payment
  claim, the threshold rule and an invalid generator (world invoices lacked the buyer reference that
  XRechnung requires, BR-DE-15) all came from running sets end to end, several on the real stack.
- **Score what is printed, or say what you score.** Scoring against the canonical invoice made a
  correct model look 2 % wrong. The answer was not to tell the model to calculate, but to keep it
  transcribing and fill gaps in code, visibly marked, with assumptions routed to a person.
- **100 % means the set is saturated, not that the problem is solved.** Synthetic PDFs are clean and the
  scan degradation is mild for a vision model. These sets can no longer rank one change against another.
- **Zero errors needs a bound next to it.** 0 of 45 sounds like a guarantee and is not one; showing
  ≤ 1 % needs about 300 automatic bookings without an error.
- **Repeated runs find what one run hides.** Run 1 booked 45 held-out invoices with no error; runs 2
  and 3, same model and prompt, each left one printed field out of the same invoice and booked it
  (worst case 1). Accuracy barely moved (± 0.04 %), the error count did.
- **Confidence built from checks and grounding is cheap and explainable, but not independent of the
  reading.** It catches values that fail a check or are absent from the page, and misses right values in
  the wrong field (cases 1 and 2).
- **Record and replay made the model eval a CI gate.** Free, deterministic, and any change to prompt,
  schema, model or document shows up as a missing recording, not as a silent drift.
- **Rules were enough for matching** ([D11](../ARCHITECTURE.md#5-design-decisions-adr-log)). They reach 100 % held-out and 99.5 % on two seeds never looked
  at; what remains is undecidable from the data for any reader. An agent would have added cost and a
  place for injected text to act.
- **Same author, same blind spots.** Generators, checks and matcher were written together. Held-out
  layouts, unseen seeds and third-party parser test files reduce that; only real data removes it.

## Known limits

- **Synthetic only.** No real invoice has been run; real layouts, handwriting, multi-page scans, foreign
  formats and messy ERP data are untested. The realism set (EVAL_PLAN §2) needs real invoices to
  anonymize.
- **Three runs.** The model is not deterministic; three runs give a mean and a spread, not a
  distribution. Injection probes ran once.
- **Small held-out sets.** 36 PDFs, 24 scans, 10 cases per exception kind, 20 probes: every 100 % here
  has a wide interval.
- **Assumed currency.** Invoices that print no currency are taken as EUR and sent to review; that default
  is not confirmed by the project owner yet.
- **Regular world.** One delivery per invoice, amounts exact to the cent, no discounts, fees, foreign
  currency or credit notes in matching.
- **Exceptions are invoice data, not files.** The exception and matching evals start after reading, so
  reading errors and planted problems never meet in one document.
- **Probes are fixed and non-adaptive**, text PDFs only: no scans, metadata, embedded XML, or text that
  imitates a field. Matching and checks use no model, so an injection can act only through extracted
  fields, which the checks then compare with the ERP.
- **Latency** (5–6 s per model call) was measured once while recording; the replay does not measure it,
  and OCR for grounding adds time on scans.
- **Not drawn:** the reliability diagram (one populated bin) and a confusion matrix for exceptions (no
  confusions to show). The auto-rate vs. error curve is the table above.
- **Ablations not run:** no local vision model is set up, and the with/without-OCR-text comparison needs
  new paid recordings.
