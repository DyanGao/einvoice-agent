# einvoice-agent

> An agent that turns incoming German invoices (XRechnung, ZUGFeRD, PDF, scans) into booked, matched and checked entries — and only asks a human when it's unsure.

Since 2025 every German business must be able to receive e-invoices; issuing becomes mandatory in 2027 (turnover > €800k) and 2028 (all). Structured XML makes *reading* invoices easy — the remaining work is **matching** them to purchase orders, delivery notes and bank transactions, catching **exceptions** (wrong VAT, price deviations, duplicates), handling **non-structured invoices** from foreign suppliers, and getting the result into **systems without an API**.

**Why this one:** structured-first pipeline (validate XML before any LLM), confidence-based human review, browser-automation fallback for legacy systems, and an eval on a labeled document set.

## Features
- [ ] Ingest: email inbox (IMAP), folder watch, upload UI, API _(built: folder watch, upload in the review UI, `POST /documents`; IMAP is not built)_
- [x] Format detection: XRechnung (UBL/CII), ZUGFeRD/Factur-X (PDF/A-3 with embedded XML), plain PDF, scan
- [x] Structured path: parse + validate (KoSIT validator / Mustang) — no LLM needed _(KoSIT only so far: ZUGFeRD profiles outside EN 16931 and PDF/A-3 conformance are not validated)_
- [x] Unstructured path: OCR + vision LLM → schema-constrained extraction (EN 16931 fields) _(the model transcribes, rules fill only what is not printed and mark it; per-field confidence from checks and OCR grounding)_
- [x] Matching: invoice ↔ PO ↔ delivery note ↔ bank transaction (3-way match + fuzzy) _(rule-based, including typos, missing references, partial and combined payments; matched again when new invoices or transfers arrive. The planned model agent was not built: on the eval world the rules leave open only what no reader could decide, and an agent would add cost and a place for injected text to act)_
- [x] Checks: VAT rate/ID plausibility, totals, duplicates, IBAN changes (fraud signal), price/quantity deviations _(against the ERP's suppliers and orders; quantity deviation is unit-tested but not in the exception eval)_
- [x] Human-in-the-loop review UI for low-confidence fields and exceptions _(upload, queue, "why a person needs to look", unsure fields marked, correct, approve or reject with a reason, reject plain duplicates together, history, delivery status)_
- [x] Decision engine: books an invoice without a person only when it was read with confidence, nothing was assumed and no check raised a finding _(75 % of held-out documents on synthetic data; ≤ 1 % error not yet shown, see Results)_
- [x] Output connectors: CSV/DATEV-style export, REST webhook, mock ERP via API, Playwright fallback for UI-only systems _(each invoice delivered once per connector, retried with backoff; the browser connector reads every booking back)_
- [x] Audit trail per document (source, extracted values, who approved or rejected and why) _(the reviewer's name comes from the UI and is not authenticated: the API has no login and is meant for localhost)_
- [x] Eval harness: labeled synthetic sets, rule-based baseline, held-out split, recorded model answers, CI gates — `make eval-full` _(no real invoices yet)_

## Quickstart
```bash
docker compose up -d --build  # postgres, redis, validator, api, worker, watch, deliver, ui, mock-erp (seeds itself)
make demo                     # processes sample_invoices/ in Docker: 5 in, 4 booked, 1 flagged — no API key
open http://localhost:3000    # review UI; the mock ERP's bookings: http://localhost:8100/ui/bookings
```
`make demo` runs on its own database and mock ERP, so the review UI and the bookings page start empty.
To see the same story there, drop the five files from `sample_invoices/` onto the review UI: four are
booked without review, the fifth waits under "To review" until you enter your name and approve it.

PDFs and scans are read by a model: put `ANTHROPIC_API_KEY` in `.env` (see `.env.example`). E-invoices need no key.
The database password `einvoice` is a local development default (every port is bound to localhost): set `POSTGRES_PASSWORD` in `.env` before running this anywhere else. It applies when the database is first created; the services log a warning while the default is used on a database that is not on this machine.
Reseed the mock ERP: `docker compose run --rm mock-erp python -m mock_erp.seed --out /tmp/world`.

For development, the same runs from source with uv and pnpm (stop the compose app services first, they use the same ports):

```bash
make up && make migrate       # postgres, redis, validator
make seed && make erp         # optional: mock ERP on http://127.0.0.1:8100
make api                      # http://127.0.0.1:8000, no authentication: localhost only
                              # with ERP_URL=http://127.0.0.1:8100 for supplier and order checks
make worker
make watch && make deliver    # optional: re-matching on new transfers, delivery to the ERP
make ui-install && make ui    # http://localhost:3000
```

## Data & privacy
- Repo contains **only synthetic or fully anonymized** invoices
- E-invoices (XRechnung, ZUGFeRD) are parsed and validated on the machine; no model sees them
- PDFs and scans are sent to the Anthropic API to be read (`EXTRACTOR=llm`, the default). To keep every document on the machine, set `EXTRACTOR=baseline` (rule-based, far less accurate: see Results) or `EXTRACTOR=none` (PDFs and scans are not read; they are marked "extraction failed: no extractor configured"). A local vision model is not built yet; it would sit behind the same extractor interface
- Not tax advice; archiving rules (GoBD) are out of scope for v1 and documented as such
